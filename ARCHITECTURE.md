# AI Study Companion Architecture

## Overview

The AI Study Companion uses a clean, scalable architecture separating concerns across the frontend, API, business services, database, background jobs, AI services, and observability. This separation ensures the system remains maintainable as new features are added in future implementation phases.

## Layered Architecture

```text
Frontend (React + Vite + Tailwind)
    ↓  HTTP via Axios
API Layer (FastAPI /api/v1)
    ↓  depends on
Authentication Dependency (get_current_user)
    ↓
Business Services (auth_service, ...)
    ↓
MongoDB (Motor async driver)
    ↓
Background Jobs (Celery / asyncio — Phase 3+)
    ↓
AI Services (Groq LLM — Phase 3+)
    ↓
Observability (logging, metrics)
```

## Phase 1 — Authentication Architecture

```text
Browser
  ↓ POST /api/v1/auth/register | login
FastAPI Route (app/api/routes/auth.py)
  ↓ validates schema (Pydantic)
Auth Service (app/services/auth_service.py)
  ↓ hashes password / verifies password
  ↓ creates JWT via create_access_token()
MongoDB users collection
```

```text
Browser (with JWT in localStorage)
  ↓ GET /api/v1/auth/me  [Authorization: Bearer <token>]
FastAPI Route
  ↓ Depends(get_current_user)
Authentication Dependency (app/api/dependencies.py)
  ↓ decode_access_token() → user_id
  ↓ get_user_by_id(user_id) → user doc
  ↓ validate is_active
MongoDB users collection
  ↓ returns UserResponse (no password_hash)
```

### Password Security
- Passwords are hashed with **bcrypt** via `passlib`
- `hash_password()` and `verify_password()` are in `app/core/security.py`
- `password_hash` is never returned in any API response

### JWT
- Tokens are signed with `JWT_SECRET` using `JWT_ALGORITHM` (HS256)
- Payload contains `sub` (user-id string) and `exp` (expiry)
- `create_access_token()` and `decode_access_token()` are in `app/core/security.py`
- The frontend stores the token in `localStorage` under `access_token`
- The Axios client attaches `Authorization: Bearer <token>` automatically

### Role-Based Authorization
- Users have `role: "user" | "admin"` stored in MongoDB
- Registration always creates `role: "user"` — the backend enforces this
- `get_current_user()` in `app/api/dependencies.py` extracts the authenticated user from the JWT
- `require_admin()` extends `get_current_user()` and raises `403` for non-admin users
- Future routes use `Depends(get_current_user)` or `Depends(require_admin)`

### Data Isolation Foundation
- **No route trusts a client-supplied user ID**
- Every protected operation resolves the user from `get_current_user()` (i.e., from the JWT)
- Future Spaces and Projects will be scoped by `user.id` from the dependency, preventing cross-user access

### 3. Business Services
This layer contains the core logic for the application, such as learning algorithms, user management, and AI coordination. By keeping this separate from the API routes, the business logic remains decoupled from HTTP mechanics.

### 4. Database / Knowledge (MongoDB)
MongoDB is used as the primary database, storing structured data and user information.
**Future Implementation:** Vector databases (e.g., FAISS or similar) will be integrated for semantic search and retrieval in later phases.

### 5. Background Jobs
Tasks like PDF processing, OCR, and embedding generation will be offloaded to background workers (e.g., Celery or native async tasks) to prevent blocking the main API thread.

### 6. AI Services
This layer abstracts the interaction with LLM Providers (like Groq) and Embedding Providers. The abstraction ensures the application is not tightly coupled to a single AI vendor.

### 7. Observability
Basic logging is configured to monitor API health and system events. Future phases will introduce comprehensive observability dashboards for AI request tracing and job monitoring.

## Database Entities (Phase 0 Documentation)

While these are not fully implemented yet, the following entities form the core of the database architecture:

* **User**: Represents a student or user. Owns Spaces and Projects.
* **Space**: A high-level category or folder (e.g., "Computer Science").
* **Project**: A specific study area within a Space (e.g., "Operating Systems").
* **Material**: Source documents (e.g., PDFs) uploaded by the user.
* **KnowledgeChunk**: Processed and vectorized pieces of a Material for retrieval.
* **Conversation**: An interaction session with the AI Tutor.
* **Message**: A single message within a Conversation.
* **Concept**: A specific learning topic extracted from materials.
* **Mastery**: Tracks the user's proficiency in a Concept.
* **Assessment**: A quiz or test generated by the AI.
* **QuizQuestion**: An individual question within an Assessment.
* **Recommendation**: AI-generated suggestions for further study.
* **ActivityEvent**: Logs user interactions for analytics.
* **AIUsage**: Tracks tokens and usage per provider.
* **BackgroundJob**: Monitors the status of asynchronous tasks like PDF parsing.

```text
│   │   ├── Mastery (Phase 5+)
│   │   ├── Growth (Phase 6+)
│   │   └── Analytics (Phase 6+)
│   └── Projects

```

### Models & Database Schemas

#### Space Model (`spaces` collection)
- `_id`: `ObjectId` (primary key)
- `user_id`: `str` (owner reference)
- `name`: `str` (1 - 100 characters, non-blank)
- `description`: `str` (max 500 characters)
- `created_at`: `datetime` (UTC timestamp)
- `updated_at`: `datetime` (UTC timestamp)

#### Project Model (`projects` collection)
- `_id`: `ObjectId` (primary key)
- `space_id`: `str` (parent Space reference)
- `user_id`: `str` (owner reference for direct security & data isolation)
- `name`: `str` (1 - 100 characters, non-blank)
- `description`: `str` (max 1000 characters)
- `learning_goal`: `str` (max 1000 characters — used by AI Tutor, Quizzes, Mastery)
- `created_at`: `datetime` (UTC timestamp)
- `updated_at`: `datetime` (UTC timestamp)

### Key Architectural Decisions

1. **Dual Ownership Tracking (`user_id` on Project)**:
   - Projects retain explicit `user_id` alongside `space_id`.
   - **Rationale**: Direct database-level queries using `{"_id": project_id, "user_id": user_id}` enforce ownership without requiring extra nested space lookups on standalone operations.

2. **Data Isolation & 404 Privacy Strategy**:
   - Authorization is derived exclusively from the authenticated user's JWT `sub` claim.
   - When a user attempts to access or modify a Space or Project that does not exist OR belongs to another user OR is accessed via the wrong Space ID, the API returns `404 Not Found` (instead of `403 Forbidden`).
   - **Rationale**: Returning 404 prevents malicious actors from probing valid resource IDs owned by other users.

3. **Cascade Deletion Strategy**:
   - Deleting a Space explicitly deletes all Projects belonging to that Space (`db["projects"].delete_many({"space_id": space_id, "user_id": user_id})`).
   - **Rationale**: Prevents orphaned child documents and preserves database integrity.

4. **Database Indexes**:
   - `spaces`: index on `user_id`
   - `projects`: index on `user_id`, index on `space_id`, compound index on `(space_id, user_id)`

### API Endpoints Summary

- `POST /api/v1/spaces` — Create Space
- `GET /api/v1/spaces` — List authenticated user's Spaces
- `GET /api/v1/spaces/{space_id}` — Get Space details
- `PUT/PATCH /api/v1/spaces/{space_id}` — Update Space
- `DELETE /api/v1/spaces/{space_id}` — Cascade delete Space & Projects
- `POST /api/v1/spaces/{space_id}/projects` — Create Project inside Space
- `GET /api/v1/spaces/{space_id}/projects` — List Projects inside Space
- `GET /api/v1/spaces/{space_id}/projects/{project_id}` — Get Project in Space (nested validation)
- `GET /api/v1/projects/{project_id}` — Get standalone Project
- `PUT/PATCH /api/v1/projects/{project_id}` — Update Project
- `DELETE /api/v1/projects/{project_id}` — Delete Project

### Frontend Route Structure

- `/spaces` — Spaces Grid/List & Create Space Modal
- `/spaces/:spaceId` — Space Details & Project List
- `/spaces/:spaceId/projects/:projectId` — Project Dashboard with Learning Goal & Materials Tab

## Phase 3 — PDF Upload & Background Processing Architecture

```text
User PDF Upload (POST /api/v1/projects/{project_id}/materials)
       ↓
Validate file format (.pdf) + file size (<=25MB) + project ownership
       ↓
Store file physically on disk + Save Material record (status = QUEUED)
       ↓
FastAPI BackgroundTasks (non-blocking async worker)
       ↓
Material Status updated to PROCESSING (Increment processing_attempts)
       ↓
Extract PDF Text page-by-page (pypdf parser, preserve 1-indexed page_number)
       ↓
Page-Aware Chunking (sliding window with overlap, retaining source page_number)
       ↓
Generate Vector Embeddings (embedding_service deterministic 64d vector builder)
       ↓
Idempotent Database Update (Clear existing chunks for material -> Insert new chunks)
       ↓
Material Status updated to READY (set processed_at timestamp)
```

### Models & Database Schemas

#### Material Model (`materials` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (parent Project reference)
- `user_id`: `str` (owner reference)
- `filename`: `str` (original uploaded filename)
- `file_path`: `str` (secure disk storage path)
- `file_type`: `str` (`application/pdf`)
- `file_size`: `int` (bytes)
- `status`: `str` (`QUEUED` | `PROCESSING` | `READY` | `FAILED`)
- `processing_attempts`: `int` (tracks retries, max 3)
- `error_message`: `Optional[str]` (sanitized error message)
- `created_at`: `datetime` (UTC timestamp)
- `updated_at`: `datetime` (UTC timestamp)
- `processed_at`: `Optional[datetime]` (UTC timestamp when status becomes READY)

#### Chunk Model (`chunks` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (project reference)
- `material_id`: `str` (parent material reference)
- `filename`: `str` (source filename)
- `page_number`: `int` (mandatory 1-indexed page number for AI Tutor citations)
- `chunk_index`: `int` (sequential index within material)
- `chunk_text`: `str` (extracted text snippet)
- `embedding`: `List[float]` (64-dimensional vector embedding)
- `created_at`: `datetime` (UTC timestamp)

### Key Architectural Decisions

1. **Mandatory Page-Number Preservation**:
   - `page_number` is preserved during page extraction and chunking.
   - **Rationale**: Future grounded AI Tutor answers require page-level citation metadata (e.g. `Source: ML_Notes.pdf — Page 14`).

2. **Duplicate Job Protection**:
   - Atomic check in `process_material_task`: if `status == PROCESSING`, worker aborts duplicate execution.
   - **Rationale**: Prevents race conditions and multiple background jobs processing the same file simultaneously.

3. **Idempotent Retry Policy**:
   - Re-running material processing clears previous chunks (`db["chunks"].delete_many({"material_id": material_id})`) before storing newly generated chunks. Max retry limit set to `MAX_RETRY_ATTEMPTS = 3`.
   - **Rationale**: Prevents orphaned or duplicated chunks on retries.

4. **Database Indexes**:
   - `materials`: index on `project_id`, `user_id`, `status`, compound index on `(project_id, user_id)`
   - `chunks`: index on `project_id`, `material_id`, compound index on `(material_id, chunk_index)`

### API Endpoints Summary

- `POST /api/v1/projects/{project_id}/materials` — Upload PDF Material & queue processing
- `GET /api/v1/projects/{project_id}/materials` — List Materials for Project
- `GET /api/v1/materials/{material_id}` — Get single Material status & details
- `POST /api/v1/materials/{material_id}/retry` — Retry background processing for failed Material
- `GET /api/v1/materials/{material_id}/chunks` — Get processed Chunks with `page_number` metadata
## Phase 4 — Knowledge Extraction & RAG Retrieval Architecture

```text
Processed Knowledge Chunks (Phase 3)
              ↓
    Knowledge Extraction Service
   ┌──────────┼──────────┐
   ↓          ↓          ↓
Concepts    Topics    Sections
   └──────────┬──────────┘
              ↓
       Project Knowledge
              ↓
  Semantic Vector Retrieval (RAG)
              ↓
      Query Embedding
              ↓
   MongoDB Vector Match (Strict project_id filter)
              ↓
    Ranked Top-K Chunks + Citation Metadata (Filename, Page Number, Score)
```

### Models & Database Schemas

#### Concept Model (`concepts` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (parent Project reference for strict data isolation)
- `name`: `str` (unique concept name per project)
- `description`: `str` (grounded concept summary)
- `source_material_ids`: `List[str]` (source material references)
- `source_pages`: `List[int]` (grounded page citations)
- `created_at`: `datetime` (UTC timestamp)
- `updated_at`: `datetime` (UTC timestamp)

#### Topic Model (`topics` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (project reference)
- `name`: `str` (broader subject domain)
- `description`: `str` (topic theme overview)
- `source_material_ids`: `List[str]`
- `source_pages`: `List[int]`
- `created_at`: `datetime`
- `updated_at`: `datetime`

#### Section Model (`sections` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (project reference)
- `material_id`: `str` (source material reference)
- `title`: `str` (section header title)
- `page_start`: `int` (start page)
- `page_end`: `int` (end page)
- `section_order`: `int` (sequence index)
- `created_at`: `datetime`
- `updated_at`: `datetime`

### Key Architectural Decisions

1. **Structured Output Validation & Deduplication**:
   - Extracted concepts, topics, and sections are parsed into Pydantic models before mutating MongoDB.
   - Re-running knowledge extraction on existing or new materials matches existing concept names (case-insensitive) and updates source page citations (`source_pages`) rather than creating duplicate records.

2. **Strict Project Data Isolation in RAG Retrieval**:
   - Vector similarity search queries MongoDB using `{"project_id": project_id}`.
   - **Rationale**: Prevents cross-project data leakage. Queries on Project A can never return chunks belonging to Project B.

3. **Grounded Citation Preservation**:
   - Search results contain `chunk_id`, `material_id`, `filename`, `page_number`, `chunk_text`, and similarity `score`.
   - **Rationale**: Guarantees that future AI Tutor answers (Phase 5) can display precise citations (`Source: ML_Notes.pdf — Page 14`).

### API Endpoints Summary

- `POST /api/v1/projects/{project_id}/search` — Perform semantic vector RAG search inside project knowledge
- `GET /api/v1/projects/{project_id}/knowledge` — Retrieve extracted Concepts, Topics, and Sections for a Project
- `POST /api/v1/projects/{project_id}/knowledge/extract` — Manually trigger or refresh knowledge extraction

## Phase 5 — AI Tutor Architecture

```text
User Question
      ↓
JWT Authorization & Project Ownership Check
      ↓
Fetch Rolling Conversation History (Last 6 Messages)
      ↓
Phase 4 RetrievalService (Strict project_id RAG Search)
      ↓
Gather Project Concepts & Material Readiness Status
      ↓
Build Grounded Tutor Context (TutorContextService)
      ↓
LLM Provider Execution (Groq / OpenAI / Mock)
      ↓
Structured Response Validation & Citation Chunk Mapping
      ↓
Persist User & Assistant Messages (MongoDB)
      ↓
Return Answer + Verified Page Citations (or Unsupported Refusal)
```

### Models & Database Schemas (Phase 5)

#### Conversation Model (`conversations` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (project reference)
- `user_id`: `str` (owner user reference)
- `title`: `str` (conversation title)
- `created_at`: `datetime` (UTC timestamp)
- `updated_at`: `datetime` (UTC timestamp)
- `last_message_at`: `datetime` (UTC timestamp)

#### Message Model (`messages` collection)
- `_id`: `ObjectId` (primary key)
- `conversation_id`: `str` (conversation reference)
- `project_id`: `str` (project reference)
- `user_id`: `str` (user/tutor reference)
- `role`: `str` ("user" | "assistant" | "system")
- `content`: `str` (message text body)
- `citations`: `List[CitationModel]` (verified material, filename, page_number, chunk_id, relevance_score)
- `grounded`: `bool` (true if grounded in evidence; false if unsupported)
- `retrieval_metadata`: `dict` (RAG latency and count metadata)
- `created_at`: `datetime` (UTC timestamp)

### Key Architectural Decisions (Phase 5)

1. **Unsupported Question Handling**:
   - When project materials are missing, processing, or when RAG retrieval returns 0 chunks above the relevance threshold (`TUTOR_RETRIEVAL_THRESHOLD`), the Tutor strictly refuses to answer from general LLM memory.
   - Response flags: `grounded=false`, `unsupported=true`, `citations=[]`.

2. **Backend-Verified Citation Mapping**:
   - Citations are NOT generated by the LLM from memory.
   - The backend maps returned chunk IDs directly back to real chunk objects stored in MongoDB (`material_id`, `filename`, `page_number`), guaranteeing page numbers are genuine and traceable.

3. **Project & User Security Isolation**:
   - All conversation and message queries enforce `project_id = current_project_id` and `user_id = current_user_id`.
   - Cross-project retrieval and cross-user conversation access are strictly prevented and covered by automated tests.

## Phase 6 — Adaptive Quiz + Open-Ended Assessment Architecture

```text
Student Selects "New Practice Quiz"
      ↓
JWT Authorization & Project Ownership Check
      ↓
AdaptiveAssessmentService
  ├── Evaluates User Attempt History & Concept Mastery Signals
  ├── Computes Priority Score per Concept (Mastery, Mistakes, Trend, Freshness, Difficulty)
  └── Selects Target Concepts & Target Difficulty Levels
      ↓
Grounded Question Generation
  ├── Retrieves Knowledge Chunks via RetrievalService
  ├── Prompts LLMProvider for Structured JSON
  ├── Validates Pydantic Output (MCQ option counts / Open-Ended format)
  └── Enforces Duplicate Prevention (Normalized Text Match)
      ↓
Persist Assessment & QuizQuestion Documents (MongoDB)
      ↓
Student Answers Question
  ├── MCQ: Deterministic evaluation against stored correct_answer
  └── Open-Ended: Qualitative LLM Evaluation against Project Evidence
      ↓
Persist QuestionAttempt & Return Result Feedback
```

### Models & Database Schemas (Phase 6)

#### Assessment Model (`assessments` collection)
- `_id`: `ObjectId` (primary key)
- `project_id`: `str` (project reference)
- `user_id`: `str` (owner user reference)
- `title`: `str` (quiz title)
- `status`: `str` ("DRAFT" | "IN_PROGRESS" | "COMPLETED")
- `question_count`: `int` (total questions count)
- `current_question_index`: `int` (current active question index)
- `score_mcq`: `Optional[float]` (calculated percentage accuracy for MCQs)
- `started_at`: `datetime` (UTC timestamp)
- `completed_at`: `Optional[datetime]` (UTC timestamp)

#### QuizQuestion Model (`quiz_questions` collection)
- `_id`: `ObjectId` (primary key)
- `assessment_id`: `str` (assessment reference)
- `project_id`: `str` (project reference)
- `concept_ids`: `List[str]` (target concept IDs)
- `concept_names`: `List[str]` (target concept names)
- `question_type`: `str` ("MCQ" | "OPEN_ENDED")
- `question_text`: `str` (question statement)
- `options`: `Optional[Dict[str, str]]` (MCQ options A, B, C, D)
- `correct_answer`: `Optional[str]` (stored correct option choice, hidden before answer)
- `difficulty`: `str` ("EASY" | "MEDIUM" | "HARD")
- `explanation`: `str` (answer explanation)
- `source_references`: `List[CitationModel]` (grounded material, filename, page_number)
- `order_index`: `int` (sequence order)

#### QuestionAttempt Model (`question_attempts` collection)
- `_id`: `ObjectId` (primary key)
- `assessment_id`: `str` (assessment reference)
- `question_id`: `str` (question reference)
- `project_id`: `str` (project reference)
- `user_id`: `str` (user reference)
- `student_answer`: `str` (option key or freeform text response)
- `is_correct`: `Optional[bool]` (true/false accuracy)
- `evaluation`: `Optional[dict]` (qualitative open-ended evaluation breakdown)
- `attempted_at`: `datetime` (UTC timestamp)

### Key Architectural Decisions (Phase 6)

1. **Multi-Signal Adaptive Target Selection**:
   - The engine evaluates mastery levels, mistake frequency, recent performance trends, time since last attempt, and unproven difficulty levels to target practice.
   - Avoids naive `correct -> hard, wrong -> easy` rules and prevents getting stuck on a single concept indefinitely.

2. **Qualitative Open-Ended Evaluation**:
   - Open-ended answers are evaluated conceptually using LLM Provider completion against retrieved Project Evidence.
   - Returns structured components: `understanding`, `accuracy`, `relevance`, `key_concepts_present`, `missing_concepts`, `reasoning_feedback`, `strengths`, `areas_to_improve`, and `suggestion`.

3. **Deterministic MCQ Verification**:
   - MCQ answers are compared directly against the stored `correct_answer` in application logic without invoking an LLM.

### Models & Schemas

#### Analytics Schemas (`app/schemas/analytics.py`)
- `ProjectAnalyticsResponse`: Structured container for project activity, quiz performance, concept growth trends, and AI operations.
- `GlobalAnalyticsResponse`: Aggregated metrics across all spaces/projects for the authenticated user.
- `AdminOverviewResponse`: System-wide counts (Total Users, Active Projects, Tutor Requests, Quiz Attempts, Failed Jobs, Health Status).
- `AdminUserItem` & `AdminUserJourneyResponse`: Paginated user accounts list and single-user chronological learning journey inspection.
- `AdminActivityItem` & `AdminActivityListResponse`: Global activity event stream with filtering by event_type, user_id, or project_id.
- `AdminEngagementResponse`: Daily Active Learners (DAL), Weekly Active Learners (WAL), and Monthly Active Learners (MAL).
- `AdminAIUsageResponse` & `AdminAIEvaluationResponse`: AI request counts, success/failure rates, tokens, latency, and groundedness percentages.
- `AdminJobsResponse` & `AdminSystemHealthResponse`: Background worker status distribution and real-time health checks (API, MongoDB, Disk Storage, AI Provider).

### Key Architectural Decisions (Phase 10)

1. **Zero Fake Data Policy**:
   - All analytics metrics, time-series charts, mastery averages, and counter badges are calculated dynamically from real MongoDB collections (`events`, `assessments`, `question_attempts`, `mastery_events`, `growth_snapshots`, `recommendations`, `conversations`, `messages`, `background_jobs`, `users`, `projects`).
   - If no evidence exists, explicit empty states are rendered instead of fake zero-like placeholders.

2. **Admin Authorization & Security Isolation**:
   - All `/api/v1/admin/*` endpoints are protected by the `require_admin` FastAPI dependency.
   - Non-admin users attempting access receive `403 Forbidden`. Admin views never expose password hashes, JWT secrets, or API keys.

3. **Performance & Query Safety**:
   - Calculations use efficient MongoDB aggregation pipelines and compound indexes (`project_id, created_at`, `user_id, created_at`, `correlation_id`).

## Why this Architecture?

1. **Decoupling**: By placing business logic in services and creating interfaces for AI providers, we can switch implementations (e.g., from Groq to OpenAI) without rewriting the API or frontend.
2. **Scalability**: Background jobs allow the system to handle heavy tasks (PDF processing) without degrading the user experience.
3. **Maintainability**: Clear separation of concerns makes it easier for multiple developers (or AI assistants) to work on different parts of the system simultaneously.
